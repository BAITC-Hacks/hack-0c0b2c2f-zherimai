# Совместная работа трёх участников и их Codex

## Общая память

Все агенты читают корневые `AGENTS.md`, `TEAM_CONTEXT.md`, `PLAN.md`, `TASKS.md`. Новые решения записываются в репозиторий; другие Codex не видят ваш чат автоматически. Git не синхронизирует рабочие папки в реальном времени: изменения становятся доступными после commit, push и получения коллегой.

До правок: проверить `git status`, текущую ветку, последние коммиты и назначение задачи. Не выполнять reset/clean, не удалять чужие изменения, не делать stash или переключение ветки вслепую. Обновлять чистую локальную main через `git pull --ff-only`; если Git сообщает расхождение или есть несохранённая работа, сначала разобрать причину.

## Ветки и результаты

- Для независимой задачи используйте отдельную ветку официального репозитория вида `codex/<задача>-<участник>`. Не создавайте отдельный внешний репозиторий для сдачи.
- В общем рабочем каталоге нельзя переключать ветку, пока другой процесс правит файлы. Сначала согласовать; отдельный checkout/worktree применим при необходимости.
- Каждый коммит идёт от настоящей настроенной учётной записи участника. Разрешение капитана на a4ns относится к его агенту, а не ко всей команде. Не делите уже готовый коммит ради имитации чужого авторства.
- Проверяйте только назначенные изменения и список staged файлов. Добавляйте конкретные файлы; не захватывайте чужую работу через безусловный `git add .`.
- Для локальных прогонов используйте `python run.py --out out-check/<задача>` и `python validate.py --out out-check/<задача>` в установленном окружении. `out-check/` исключён из Git. Итоговые отслеживаемые `out/` обновляет интегратор после объединения.
- Push задачи делает результат доступным коллегам, но не включает его автоматически в main. Изменения должны попасть в официальный main до дедлайна; способ интеграции команда выбирает по ситуации, без force push и без уничтожения чужой истории.

## Согласованные интерфейсы

- `load_data(Path)` возвращает nodes, edges, transactions, DiGraph с полным набором узлов.
- `build_viewer(nodes_df, edges_df, clusters_df, out_path)` создаёт один автономный HTML. Идентификаторы в браузере строковые.
- Схемы трёх обязательных CSV неизменны; новые признаки добавляются колонками с документированным смыслом.
- Пороговые правила находятся в `aml/roles.py`, формула приоритета — в `aml/priority.py`; UI не создаёт вторую независимую классификацию.
- При изменении контракта перечислите затронутые модули и совместно обновите потребителей. Не маскируйте отсутствующий признак нулём, если это меняет смысл вывода.

## Проверка и передача

Для изменения логики выполните затронутые содержательные тесты и полный сценарий, если меняются выходы. Для текста — сверку с кодом и ссылками, без бессмысленного повторения вычислений. Не объявляйте проверку пройденной по чужому сообщению: укажите, чья и на каком коммите она была.

Передать капитану или интегратору:

```text
Задача / участник:
Ветка и commit:
Изменённые файлы:
Что изменилось для аналитика:
Проверки и фактический результат (среда, команды, измерения):
Что не проверено / ограничения:
Зависимости от других изменений:
Следующий шаг:
```

При необходимости сохраните эту запись в отдельном файле `docs/handoffs/<задача>-<участник>.md`, чтобы не конфликтовать в одном общем журнале. После интеграции обновить соответствующие строки TASKS и, только если изменились решения, TEAM_CONTEXT/PLAN. Не переписывать исторические измерения как будто они относятся к новой версии.
